# 0004 渐进披露与预算

- 状态：已接受
- 日期：2026-10-25

## 问题

v1 是单文件 300 行，全部内容常驻上下文。其中大部分细节只在特定分支需要：词汇三级阶梯只在定位失败时用，六类中间物只在生成时用，四类映射只在跨域迁移时用。常驻成本固定，任何细节修订都要改运行时文件，改动面与风险都大。

拆分本身不解决复发。如果没有行数与字符上限，SKILL.md 会在后续修订中重新吸收细节，回到单文件状态。

## 决策

入口只保留承重件：默认未判的入口、三种缺口与门禁、实例化、代价与排序、输出契约、硬性禁止、按需加载表。其余内容拆成 7 个专题文件，放在 `references/`，由 SKILL.md 的按需加载表触发读取。

预算由 `scripts/budget.json` 与 `budget` gate 检查。达到上限 90% 以上输出警告，超过上限失败。`docs/archive/` 与 `CHANGELOG.md` 不参与预算。

## 备选方案

- 单文件 300 行：上下文成本固定，任何分支都要读完无关细节；每次修订都触碰运行时入口，回滚范围大。
- 全量拆 references：入口变成目录，模型必须先读多个文件才能开始执行；门禁表与输出契约被拆散，运行时一致性无法保证。
- 只拆 7 个专题、不设预算：拆分只解决一次。没有上限，SKILL.md 会随修订重新膨胀，且提交时没有任何信号。
- 按主题拆成更多小文件：加载次数增加，路由表变长，维护成本高于收益；专题边界也会变得难以判定。

## 后果

运行时入口小且稳定，细节只在需要时加载；预算把「小入口」变成每次提交都能检查的约束，达到 90% 时先警告，留出余量。

风险是模型不读 references 就作答。缓解有两层：SKILL.md 的按需加载表给出具体触发条件；行为评测包含必须使用细节的用例，例如 case-02 要求落到标准号与数值。

预算超限的处理顺序是搬迁、压缩、提上限。提上限必须在 PR 说明为什么内容确实需要更多空间。
