# 0005 description 绑定显式调用

- 状态：已接受
- 日期：2026-10-25

## 问题

v1 的 description 同时说了两件相反的事：仅在用户明确要求时使用；以及问题没有标准答案、目标模糊、直搜失败时该用。Router 只能读 description，看不到用户意图之外的东西。问题的开放性不是文本里的可观察字段，而且几乎所有难题都「没有标准答案」，所以按开放性判断会把普通技术问答、调试、选型、决策咨询全部拉进来。

触发条件写成问题的属性，等于要求 router 在调用前判断一个它无法观察的性质。判断错了也没有反馈：用户不会因为一次误触发而留下可读的信号。

## 决策

触发绑定到显式施为句。用户在请求里点名方法（`open-problem` 或「开放性问题方法论」），或明确要求「先拆解再回答、不要直接给答案」时触发。description 同时写出负例：普通问答、检索、调试、选型、决策咨询一律直接回答；不因为问题开放、模糊、没有标准答案而激活。

显式施为句是用户对方法本身发出的指令，可在文本中观察，与问题难度无关。它把「是否使用本方法」的决定留给用户，而不是留给 router 猜测。

## 备选方案

- 按问题开放性触发：开放性对 router 不可观察，且与所有难题相关；这是误触发的主要来源。
- 关键词触发：用「怎么」「如何」「值得吗」等词判断。这些词大量出现在普通问答里，无法区分用户是要方法还是要答案。
- 按问题长度或复杂度触发：长度与是否需要拆解不相关。长问题可能只是信息多，短问题可能需要完整拆解。
- 让模型先判断问题是否开放再决定：判断本身需要一次模型调用，成本高且不稳定；误判发生在调用前，无法拦截。

## 后果

触发可预测、可测：router_cases 至少 3 条正例与 3 条负例，负例覆盖技术问答、调试、选型、推荐。误触发率可以通过新增负例持续压低。

代价是用户必须知道方法名或明确要求拆解，本方法不会在用户最需要时自动出现。这个代价被接受：自动触发的误伤成本高于漏触发成本。
