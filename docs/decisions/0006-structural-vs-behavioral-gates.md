# 0006 结构门禁与行为门禁分离

- 状态：已接受
- 日期：2026-10-25

## 问题

v1 没有任何自动检查。frontmatter、结构、术语、预算、链接都靠人看；即使这些都正确，也无法知道输出是否真的执行了探针。两类检查混在一起会产生冲突：结构检查要求快、确定、每次提交都跑；行为检查需要模型与额度，慢且不完全确定。

如果没有结构门禁，文档与运行时文件会漂移。如果没有行为门禁，结构正确的提示词仍然可能输出一段没有执行证据的散文。v1 的六段模板就是结构完整的输出，但它不能证明执行。

## 决策

门禁分两层。结构门禁由 `python3 scripts/check.py --all` 执行，每次提交运行，检查 frontmatter、结构、预算、链接、引用、ADR 格式、版本、术语、用例结构与语料。门禁自身由 `python3 scripts/test_gates.py` 做破坏测试，CI 每次运行。行为门禁由行为评测执行，发布前运行，对固定输入 grep 输出中的执行证据。

第三层是人工评审：语义质量、评测结果的解释、description 是否会在普通问题误触发。这三类判断没有稳定观察量，不进入自动门禁。

## 备选方案

- 只做结构门禁：便宜、稳定、每次提交可跑，但无法区分执行与描述。v1 的结构并不差，仍然失效。
- 只做行为门禁：需要模型与额度，慢且不完全确定；每次提交都跑会阻塞开发，失败也难以定位到具体文件或规则。
- 用 LLM judge 代替正则评测：增加一次模型判断，评分不稳定、不可复现，judge 本身还会受输出中的指令影响。对固定观察量做正则可审计、可重跑、成本低。
- 全部人工评审：不可扩展。评审者需要每次重读运行时文件并手动跑用例，且无法在提交时拦截结构漂移。

## 后果

提交快，结构门禁目标在 1 秒内完成；发布前有行为证据；两层失败时定位方式不同，结构失败给出文件与行号，行为失败给出未命中的正则。

风险是正则断言被「表演」文本命中。缓解是优先用正向证据（标准号、数值、未判状态），负向断言只用于结构特征（台账表头、并列模板），并要求用例定期复核。行为评测是发布门禁，不是每次提交门禁，这一点写在 `docs/verification.md`。
