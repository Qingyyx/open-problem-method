# 0009 评测用例只在本机

- 状态：已接受
- 日期：2026-10-28

## 问题

行为用例的输入来自真实客户场景，包含可识别的人物、地点、经营数据与客户结构。把它们提交到版本库，会让隐私信息随仓库、CI 日志、发布包和 fork 扩散；即使之后删除，历史提交仍然保留。

结构门禁又要求用例可解析，导致 `make check` 依赖 `evals/cases.yaml`。用例一旦不在仓库里，CI 与全新检出就无法运行该 gate。

## 决策

`evals/cases.yaml` 与 `evals/router_cases.yaml` 只在本机维护，加入 `.gitignore`，从版本库追踪中移除。用例可以带 `review` 人工清单；没有 `must_match` 的用例按人工用例运行，由人逐条判断。

`evals` 结构 gate 从 `make check` 移除，结构门禁从 10 个降为 9 个。`run_evals.py --plan` 在人工运行时校验 YAML 与正则。`make eval` 只由人工执行；AI 不自动触发，CI 不运行，结果不回写仓库。

公开的触发原则与评测方法仍放在 `evals/README.md`，但不包含任何具体客户输入。

## 备选方案

- **脱敏后入库**：保留自动评测与 CI。否决理由：脱敏会丢掉让用例成立的私有条件（城市、客单价、客户关系、渠道限制），用例变成另一个问题；而且脱敏是否彻底无法用 gate 证明。
- **加密用例后入库**：仓库里只放密文。否决理由：密钥仍要分发，CI 无法在无密钥时校验；密钥一旦泄露，历史密文同样暴露，隐私风险只是延后。
- **保留 gate，缺失时跳过**：`make check` 在无用例时跳过 eval gate。否决理由：全新检出永远跳过，gate 等于不存在；本地与 CI 的检查结果不一致，失败无法复现。
- **只删用例、保留 gate**：否决理由：CI 没有用例文件，gate 必然失败；把文件排除在检出之外又会让本地与 CI 分叉。

## 后果

- 隐私面缩小：真实客户输入不再进入 git 历史、CI 日志、发布包或 fork。
- 自动评测退化为人工评测：发布前必须由人运行 `make eval` 并逐条读输出，不能只依赖 CI 绿灯。
- 结构门禁少一个：`make check` 不再验证用例 YAML；这项校验移到 `run_evals.py --plan`。
- 历史输出与思维链只在本机：`evals/reference/` 保存原始 JSON、正文、思维链与检索记录；`evals/runs/` 保存每次人工运行的原始输出。两者都 gitignored。
- 触发样本同样只在本机：`router_cases.yaml` 不再入库，触发判断完全依赖人工抽样。
- 剩余风险：人工步骤可能被跳过。缓解是把 `make eval` 写进发布序列与评审清单，并在 `CHANGELOG.md` 的 Migration 段说明。
