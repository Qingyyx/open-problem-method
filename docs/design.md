# 设计：从 v1 失效到 v3 结构

## 问题：v1 为什么在实践中失效

v1 的失效不是某一句话写错，而是一条可重复的因果链。每一步都由上一步直接推出：

| # | 环节 | 机制 | 后果 |
|---|---|---|---|
| 1 | 首问谓词近乎恒真 | 第一个问题是「这个答案，别人已经知道了吗」。对几乎任何问题都可以答「是」：任何问题都可能在某处有过某种答案。 | 判定在第一步通过。 |
| 2 | 贪心首匹配 | 四个问题按顺序问，命中即停，不要求多个条件同时成立。 | 大多数请求被归入第一个分支。 |
| 3 | 分支吸收 | 「检索型」接收大部分请求，其余三型缺少真实样本。 | 分类表看起来完整，实际只有一个分支在被使用。 |
| 4 | 唯一硬门禁只覆盖该分支 | 只有检索型有可执行门禁：下沉到规范层，拿到标准号与数值阈值。 | 门禁的有效范围等于一个分支。 |
| 5 | 门禁静默失效 | 非工程问题没有标准号与数值阈值，门禁无法执行，也不会报错。 | 缺省路径等于没有门禁。 |
| 6 | 回到默认行为 | 没有可失败的检查，模型回到直接回答。 | 输出与不使用本方法时相同。 |
| 7 | 六段模板可被不执行而填写 | 重构后的问题、形态判定、候选路径、中间物、第一步、失败点，六段都是陈述句。 | 不跑任何探针也能写出完整交付。 |
| 8 | 执行与描述不可区分 | 模板不要求状态、代价、证据来源或失败信号。 | 读者无法判断输出背后有没有动作。 |

这条链自我强化。第 1 步恒真让第 3 步的分类看起来已完成，第 4 到 5 步的门禁因此只在一个分支上生效；第 8 步又让失败不可观察，所以没有信号回到第 1 步。

v1 的门禁内容本身不弱：隔音例子能落到 GB 50118 与 dB 阈值。弱的是覆盖范围与可失败性。门禁只在一个分支上有定义，其他分支既没有门禁，也没有「门禁不适用」的显式状态，于是静默跳过。

## 五条设计原则

| 原则 | 切断的环节 | 在 v2 的落点 |
|---|---|---|
| 探针先于分类 | 1 到 3 | 入口固定为「未判」，类型只由 P0 探针结果产生。 |
| 门禁挂断言 | 4 到 5 | 三种缺口各有门禁；门禁检查的是断言，不是分支标签。 |
| 输出必须是动作 | 6 到 8 | 台账每行要求状态与代价；下一步要求执行者、工具、耗时、花费上限、失败信号。 |
| 每条路径强制实例化 | 7 | 任何答案交付前必须列出会翻转结论的私有条件。 |
| 成本与停止条件显式 | 8 | 代价四元组、排序规则与停止条件进入输出契约。 |

原则之间不是并列清单。探针先于分类解决标签发生得太早；门禁挂断言解决门禁只覆盖一个分支；输出必须是动作解决执行不可见；强制实例化解决通用答案；成本与停止条件解决探索没有边界。

## v2 结构（v3 沿用）

```
入口「未判」
  → P0 探针（≤15 分钟）
    → 一次闭合且无私有条件 → 直接回答，不建台账
    → 定位缺失（闭合 / 未闭合）/ 生成缺失 / 证据缺失
      → 实例化（列私有条件）
        → 过程文档（7 节；第 3 节是缺口台账）
```

| 节点 | 产物 | 失败表现 |
|---|---|---|
| 入口 | 状态「未判」 | 没跑探针就贴类型 |
| P0 探针 | 一次定向检索加一次自问的结果 | 用泛泛搜索代替定向检索 |
| 三缺口 | 一行或多行缺口，各自带门禁 | 把同一缺口拆成并列方案 |
| 实例化 | 最多 5 条数值或二值的私有条件 | 只给通用对比表 |
| 过程文档 | 7 节文档，第 3 节是缺口台账；含一个下一步与停止条件 | 只给最终结论，或给两条以上并列路径 |

逐条规则、门禁表与输出契约只在 [SKILL.md](../SKILL.md)，这里不复述。门禁的检查方式与分层见 [docs/verification.md](verification.md)。

## v3：过程文档

v2 的台账解决了"有没有执行"，没有解决"过程是否可复查"：回答可以只给最终台账，读者看不到探针、来源与未验证项。v3 把输出载体改为过程文档，固定 7 个二级标题，台账成为第 3 节。文档同时写入 `open-problem-<slug>.md`，回答正文就是文档本身。

只给最终结论、把多步合并成一段、或省略执行记录，都算未完成。理由与被否决的方案见 [0007](decisions/0007-process-document-output.md)。

## v3.1：推理门禁

v3 的门禁全部挂在外部证据上：取到数值、条款、编号就算闭合。它没有约束从证据到因果的那一步。一次小样本失效：10 个客户、转介绍到店 1–2 人未成交，被判定为"口碑结构性关闭"；实际 1–2 ÷ 10 ＝ 10%–20%，与行业老带新率持平，失效的是转化率与基数，不是口碑。

v3.1 在 §2 增加推理门禁：关系式、比率基准、反证观测、断言强度；结论分为观测级、推断级、叙事级，只有前两级可以写「已闭合」。细节在 [references/reasoning-gate.md](../references/reasoning-gate.md)，取舍见 [0008](decisions/0008-reasoning-gate.md)。

## 与 v1 的差异

| 维度 | v1 | v2 |
|---|---|---|
| 分类轴 | 四个是/否问题自判形态，先分类再行动 | 分类是探针的输出；「未判」是合法入口 |
| 入口状态 | 隐含在第一步判定里 | 显式固定为「未判」 |
| 输出契约 | 六段散文模板，要求至少 3 条候选路径 | 7 节过程文档，第 3 节是缺口台账 |
| 参考层 | 单文件内嵌全部细节，约 300 行 | 承重件留在入口，7 个专题按需加载 |
| 触发方式 | 按问题是否开放推断 | 仅在用户显式点名方法或要求先拆解时触发 |

## 非目标

| 非目标 | 原因 | 边界 |
|---|---|---|
| 不自动触发 | 开放性不是 router 可观察的字段，按它触发会拉入普通问答 | 用户必须点名方法或明确要求先拆解 |
| 不执行检索 | 实际搜索、抓取、比对由 `resource-hunting` 承担 | 本方法只产出探针、判定与下一步 |
| 不替代领域知识 | 门禁要求取到权威载体，不要求模型记住领域结论 | 领域结论来自载体，方法负责找到并验证载体 |

## 有效性证据

行为用例只在本机 `evals/cases.yaml` 维护：含真实客户信息，已 gitignore，不入库、不进 CI。人工运行 `make eval`，按每条用例的 `review` 清单逐条判断；有稳定观察量的用例仍写 `must_match`。历史会话的原始 JSON、正文、思维链与检索记录保存在 `evals/reference/`，每次人工运行的原始输出保存在 `evals/runs/`；两者都 gitignored。

v3 曾覆盖三种缺口、实例化、不可逆决策、停止条件与过程文档；这些历史用例已随隐私策略从本机移除。case-07 曾专门约束过度拆解：v1 的模板要求至少 3 条候选路径；v2 在 P0 一次闭合且无私有条件时直接回答，不建台账。v3.1 保留的本地用例是一个小样本获客场景：原输出把「10 个客户只带来 1–2 人」判成口碑结构性关闭，正确路径是先算转介绍率、给参照类、写反证观测，再给一个下一步。

结构门禁检查形式，人工评测检查执行，两者不能互相替代。人工评测是发布前步骤：它需要模型与额度，单次运行慢且不完全确定，因此不进每次提交的检查。每次提交只跑结构门禁，发布流程见 [docs/releasing.md](releasing.md)。
